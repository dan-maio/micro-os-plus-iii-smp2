0. About this document

This document compares the build and test system of the smp branch (this workspace: micro-os-plus-iii and the ports -aarch32, -aarch64, -cortexm, -posix-arch) with the upstream single-core project https://github.com/micro-os-plus/micro-os-plus-iii.git, branch xpack-development, and with the xPack way that upstream follows.

  • Part A states the upstream / xPack principles (from their own documentation), shows what smp does differently, and judges each difference against those principles.
  • Part B is a plan to bring smp back to the upstream way, step by step.

Sources. Every principle is taken from a document, with its location:

  • upstream xpack-development: README-DEVELOPER.md, README-MAINTAINER.md, tests/README.md, and the code;
  • the xpm documentation, https://xpack.github.io/xpm/ (CLI pages for link, install, run, uninstall; metadata pages; the CMake integration guide; the folders page);
  • the xPack site, https://xpack.github.io/;
  • the µOS++ site, https://micro-os-plus.github.io/ (the v7.0.0 release post, the “modular projects” page);
  • for the smp side: the commit messages of the harness commits, docs/smp-integration/xpack-dev-smp.md, and the code.

Correction of the first version of this document. The first version explained the smp deviations mostly in their own terms and presented them as sound choices. Several of them contradict the upstream / xPack principles. This version judges each one against those principles. Where a question is not answered by any document, it says so.

Part A: The principles, and where smp differs

1. The upstream / xPack principles

# Principle Source
P1 Every component is a separate package with its own version. Consumers install released, read-only copies. xpm metadata pages; µOS++ “modular projects”: components are “stored as one or more files in separate packages”, each with “metadata, to define its own identity and a list of dependencies”
P2 Writable working copies are used through xpm link, in two steps: xpm link in the working copy (creates .link in the global store), then xpm link <package> in the project. -c/--config links “into an existing configuration build folder”. This is the tool for developing several packages at the same time. https://xpack.github.io/xpm/docs/cli/xpm/link/; upstream README-DEVELOPER.md (“Use development writable packages”)
P3 Tools are binary xPacks, installed once per version in a shared store and linked into each project / build configuration (xpacks/.bin, build/<config>/xpacks/.bin). Several versions can coexist; each configuration pins its versions. xpm folders page: “installing a single read-only instance in a central folder and creating links from the project to that folder”; install --config, run --config pages
P4 One build configuration per platform / toolchain / build type, each with its own build folder (buildFolderRelativePath, default build/<config>) and its own dependencies. xpm buildConfigurations and properties pages
P5 The library is added by its tests with add_subdirectory(".." "top-bin"); other packages come from xpacks/…. Plain CMake, INTERFACE targets. xpm CMake integration guide; upstream tests/cmake/tests-main.cmake
P6 Each package tests itself, in its own tests/ folder, a separate xpm project with its own package.json. xpm user guide: “move all test-related metadata to a separate tests folder, with its own package.json”
P7 The same test sources run unchanged on all platforms, with many toolchains. upstream tests/README.md: “Exactly the same source files are used on all platforms, without changes”; “compile the sources with as many toolchains as possible, and run them on as many platforms as possible”
P8 Portability: Windows, macOS, GNU/Linux. Actions are shell commands, but must be portable. xPack home: “across multiple platforms (Windows, macOS, GNU/Linux)”; upstream tests/README.md: “The tests are performed on GNU/Linux, macOS and Windows”; xpm actions page: “many Unix shell commands do not have direct equivalents on Windows” → use portable tools
P9 Board support is layered: architecture, device, board. µOS++ “modular projects”: “not monolithic, but modular, with three explicit layers”: board, device, architecture. Upstream IIIe: the port (-cortexm) is architecture only; chip files are in the test platform’s device/ folder or in third-party xPacks (arm-cmsis, raspberrypi-pico-sdk-xpack)

Note on IIIe vs IVe: the µOS++ v7.0.0 post says v7.0.0 “will hopefully be the final release of µOS++ in the current monolithic structure (IIIe)”; IVe moves to “a modular structure, based on xPacks”. So in IIIe the kernel is one package, but the ports, the tools and third-party code are already separate xPacks, and P1–P9 apply to them.

1.1 Upstream as it is today (reviewed 2026-11-17)

Checked directly against GitHub micro-os-plus/<repo>, branch xpack-development, fetched into the repositories here without adding a remote: kernel 43ef532f (2026-10-08), -cortexm 687e975, -posix-arch 49282e6.

  • Since the copy this plan was first built on (7f1ce5ca), upstream took about 30 kernel commits, mostly single-core fixes that came out of the SMP work (rtos, estd, posix-io, semihosting, ARMv8-M exception handlers). In the build and test system only three QEMU device files changed (two MPS2 linker-script comments, the FPU enable in system-cortexm.c). Everything below still holds.

    • project-level devDependencies: cmake 3.26.5, ninja-build 1.11.1, build-helper ^2.17.0, arm-cmsis-rtos-validator, chan-fatfs (the last three "local": "link");

  • CMake chain: tests/CMakeLists.txt (C11, C++20, enable_testing, no in-source builds, loads build-helper) → cmake/global-definitions.cmake (ENABLE_RTOS_APIS_TEST, ENABLE_MUTEX_STRESS_TEST, ENABLE_CMSIS_OS_VALIDATOR_TEST) → cmake/tests-main.cmake:
    1. common-options.cmake, then the platform’s definitions.cmake and dependencies-folders.cmake;
    2. xpack_add_dependencies_subdirectories(…) first: the suites (sources/<suite>), the port and chip packages from build/<config>/xpacks/…, the device folder, and the project-level xpacks/… (validator, FatFs);
    3. then add_subdirectory(".." "top-bin"), the kernel;
    4. then add_subdirectory("platforms/${PLATFORM_NAME}" "platform-bin"). All targets are INTERFACE libraries, so the port can be added before the kernel: links by name are resolved when CMake generates.
  • A platform: definitions.cmake (platform and device compile definitions, linker script name); dependencies-folders.cmake; platform-library.cmake (micro-os-plus::platform: -mcpu, float ABI, -Werror, links micro-os-plus::iii-<port> + micro-os-plus::device); CMakeLists.txt (adds device/ if the platform has one, then one add_test_executable + add_test per enabled suite, the add_test calling qemu-system-arm …, openocd … program … reset, or the program).
  • Device: micro-os-plus::device comes from tests/device-qemu-cortexm/ for the QEMU machines, from the platform’s own device/ for NUCLEO and Pico, plus chip xPacks (arm-cmsis, raspberrypi-pico-sdk, SEGGER). The NUCLEO CMakeLists.txt has “TODO: update to separate device-stm32f4-extras, when ready”: upstream itself plans separate device packages (D3).
  • Ports: CMakeLists.txt is a plain INTERFACE library (micro-os-plus::iii-cortexm, ::iii-posix-arch) with include/ and src/rtos/os-core.cpp; package.json has no dependencies; test/ holds only .gitkeep.
  • CI: three GitHub workflows run npm --prefix tests ci, then xpm run install-ci|install-all -C tests and xpm run test-ci|test-all -C tests, with xpm 0.20.8, on Ubuntu x64 and arm64, macOS Intel and Apple Silicon, and Windows.
  • An upstream inconsistency to fix in step 2: native-dependencies declares @micro-os-plus/posix-arch, but the package’s own name, the native-actions link-deps and the native dependencies-folders.cmake all use @micro-os-plus/micro-os-plus-iii-posix-arch.

2. What is the same, and what differs

The same. The outer mechanism: xpm configurations in tests/package.json (P4), tools from the shared store (P3), CMake + Ninja to build, CTest to test, and the same commands (xpm run install --config <C>, xpm run test-<platform>-cmake). The harness folder micro-os-plus-iii/tests/ has every upstream file, and all 24 platforms have the same five upstream platform files.

What differs, in short:

Upstream smp
Finding the ports xpm dependency + xpm link sibling folder, path computed by CMake
Who adds the kernel the tests (add_subdirectory("..")) the port
Chip and driver code platform device/ or separate xPacks inside the ports (soc/, drivers/); the devices repository was dissolved
Board facts the platform folder the port’s test/boards/<b>/board.cmake and the platform folder; the port library itself reads board.cmake
Tests portable suites in the kernel’s tests/ the same, plus board tests in <port>/test/<board>/<app>/, registered into the kernel’s harness
Running a test CTest runs qemu / openocd / the program the same for upstream suites and Cortex-M QEMU; bash scripts for AArch QEMU, native board tests and hardware
Verdict exit code RESULT: line, plus exit code

2.1 Where bash is used

Building uses no bash: the build steps run only the compiler, objcopy and cmake -E. The one script in a build is upstream’s own build-helper/dev-scripts/get-libraries-paths.sh (native platform).

Running uses bash for the test kinds upstream does not have:

Test kind Upstream: CTest runs smp: CTest runs
Upstream suites on QEMU (qemu-cortex-m*, 2xcortex-m33, pico2-1cpu) qemu-system-arm … the same
Cortex-M board tests on QEMU (none) qemu-system-arm … directly
Native validator the program the same
Native board tests (none) bash run-host.sh
AArch32 / AArch64 board tests on QEMU (raspi3b) (none) bash run-qemu.sh
Hardware tests openocd -c "program …" -c reset bash <board>/hw.sh → bash run-hw.sh

3. Each difference, the reason given at the time, and the verdict

The reasons are the ones written down when the change was made (commit messages, xpack-dev-smp.md, script headers). The verdict compares them with §1.

3.1 Sibling folders instead of xpm link — against P1, P2

Reason given: the kernel and the ports change together, so a released port never matches the kernel under development; and several copies of the same repositories existed on the machine, while the .link registry holds one path per package.

Verdict: the first reason is exactly the case xpm link exists for: developing several packages at once from writable working copies (P2). The second is not an xPack scenario. The xpm docs show one development copy per package and do not discuss several (not covered). Several copies of the same package is a situation this project created, not a limit of xPack. The reason does not hold.

3.2 The port adds the kernel — against P5

Reason given (commit K44): “the harness added the kernel one level up and each port as an xpack dependency, so a port could not bring its own kernel, devices or board.”

Verdict: P5 is the documented pattern: the tests add the library, the other packages are dependencies. A port that brings the kernel turns the dependency upside down. The ports only add the kernel if (NOT TARGET …) already, so going back is small (§8). Does not hold.

3.3 Chip and driver code moved into the ports; devices dissolved — against P9

Reason given (xpack-dev-smp.md §3.1): register definitions for one chip were split between two repositories, and a change needed matching commits in both.

Verdict: P9 asks for separate architecture, device and board layers. The fix for “one chip split over two repositories” is one package per chip family, not folding all chips into the architecture port. The two-repository commit is what xpm link handles (P2). Does not hold.

3.4 Board facts in the port (board.cmake) — against P9

The port library reads test/boards/${BOARD}/board.cmake to know its SoC and CPU count, and the platform folder reads it again. Example, the Pi 4 B: SoC, -mcpu, CPU count, linker script, LED pin and SD address are in micro-os-plus-iii-aarch64/test/boards/rpi4b/board.cmake; BOARD=rpi4b is in the platform’s definitions.cmake; platform-library.cmake uses the CPU count and linker script from the port, and sets some defines the port’s test builder sets again. A board is described in three files in two repositories, and the architecture package knows boards. Does not hold.

3.5 Board tests in the ports, registered into the kernel’s harness — against P6, P7

Reason given: SMP bugs depend on the chip (secondary core start-up, inter-core interrupts, caches with DMA, PSRAM…), and a test belongs next to the code it tests.

Verdict: the need is real: SMP must be tested on real chips. The place is wrong. The kernel’s tests/ must run the same sources on all platforms (P7), and chip-specific programs break that. Under P6, a test of the architecture port belongs in the port’s own tests/ project, a driver test in the device package’s tests/. The kernel’s harness should not register them.

3.6 Tests found by folder instead of listed by hand — compatible

The xpm guide says of the tests folder: “The name of the folder and the hierarchy below it are all at author’s discretion.” How CMake registers tests is a CMake detail. With more than 200 programs, a folder scan is reasonable. It stays, but inside each package’s own tests/ (§10).

3.7 One source built for QEMU, hardware and host — compatible

Running the same sources on many platforms is P7 itself.

3.8 Bash runner scripts — against P8

Reason given: QEMU boot shim, SD card image, timeouts; on hardware: halt all cores, load, start core 0, resume parked cores, separate reset sessions. run-hw.sh replaced 48 nearly identical copies.

Verdict: the multi-core steps are needed, but bash scripts do not run on Windows (P8). xpm allows shell commands in actions if they are portable; these scripts are not. They can be replaced by CTest settings and OpenOCD Tcl (§11).

3.9 The RESULT: line — compatible

An extra, human-readable verdict; CTest can read it itself (PASS_REGULAR_EXPRESSION…). The exit code stays. Note: the comment in hw_result.hpp saying QEMU builds have no SEMIHOST is out of date; the AArch builds define it and QEMU runs with semihosting on.

3.10 Hardware tests opt-in (hwd label) — compatible

xpm run test-all must work with no board connected.

3.11 Upstream platforms kept; more configurations — compatible

The upstream platforms still run the upstream suites (single-core regression), and the new platforms are configurations of the same kind (P4). There are 90 non-hidden configurations (upstream: 44).

Part B: How to bring it back

Nothing below has been applied. Each step is one or a few commits, and keeps the tests green.

4. The target, in one picture

    platforms/<P>/                one place per board: flags, linker, CPU count, device link (P9)

All of them are xpm dependencies of each other with released versions; working copies are plugged in with xpm link (P1, P2). Tools come from the shared store (P3). Everything runs on Windows, macOS and Linux (P8).

6. Step 1: the port is a leaf; the tests add the kernel (R1, R2, R5)

tests/cmake/tests-main.cmake, exactly in upstream’s order (§1.1): dependencies first, then the kernel, then the platform.

include ("cmake/common-options.cmake")
include ("platforms/${PLATFORM_NAME}/cmake/definitions.cmake")
include ("platforms/${PLATFORM_NAME}/cmake/dependencies-folders.cmake")
xpack_add_dependencies_subdirectories (                 # suites, the port, chip
  "${xpack_dependencies_folders}" "xpacks-bin")         # packages: build/<config>/xpacks/
add_subdirectory (".." "top-bin")                       # the kernel
add_subdirectory ("platforms/${PLATFORM_NAME}" "platform-bin")

(xpack_add_dependencies_subdirectories comes from upstream’s @micro-os-plus/build-helper, not from xpm; xpm itself uses plain add_subdirectory.)

Each port platform’s dependencies-folders.cmake lists the port, as upstream does for micro-os-plus-iii-cortexm:

"${CMAKE_BINARY_DIR}/xpacks/@micro-os-plus/micro-os-plus-iii-aarch64"

Each port’s CMakeLists.txt loses its “find the kernel next to me” block and becomes a plain INTERFACE library like upstream’s -cortexm. It must not test whether the kernel target exists (if (NOT TARGET …)), because the port is added before the kernel; it links kernel targets by name, which CMake resolves when it generates. The aarch ports’ current if (NOT TARGET micro-os-plus::iii-core) guards go for the same reason.

Check: prepare + build of all platforms, then xpm run test-all.

7. Step 2: dependencies as xpm packages, working copies via xpm link (R3, R4, R5)

Versions. Tag each package with a pre-release version, as README-MAINTAINER.md describes for the kernel (7.1.0-pre.1 style). For example micro-os-plus-iii-cortexm v2.0.0-pre.1 (a major bump: the CMake shape and the kernel it needs changed), -aarch32 / -aarch64 v0.1.0-pre.1.

Declaration, in tests/package.json, the same shape as upstream’s cortexm-dependencies:

"aarch64-dependencies": {
  "hidden": true,
  "devDependencies": {
    "@micro-os-plus/micro-os-plus-iii-aarch64": {
      "specifier": "github:dan-maio/micro-os-plus-iii-aarch64#v0.1.0-pre.1",
      "local": "link",
      "platforms": "all"
    }
  }
}

The POSIX port uses glibc’s ucontext by choice, so upstream’s @xpack-3rd-party/libucontext dependency does not come back.

Working copies, exactly as upstream. Once per machine, in each working copy: xpm link (step 1). Per configuration, in the tests: xpm link @micro-os-plus/micro-os-plus-iii-aarch64 --config <C> (step 2, upstream’s link-deps action). Upstream’s layout is one clone per package, side by side in one folder, each linked once.

One working copy per package, all in this workspace (D1). The store holds one .link per package name. Every .link of these packages points into /home/dan/Desktop/micro-os-plu-iii-smp-pr-github/, and to no other folder.

Hardware scripts, while they still exist: reached through build/<config>/xpacks/…, hw.sh cannot find the kernel from its own path; CTest passes UOS_SMP_DIR=${CMAKE_SOURCE_DIR}/.. in the test’s ENVIRONMENT. This goes away with §11.

Check: the prepare log shows the port under build/<config>/xpacks/@micro-os-plus/…; the same tests pass.

8. Step 3: device packages (R6)

Move each chip family’s code out of the ports into its own xPack, following P9 and upstream’s use of chip xPacks (arm-cmsis, raspberrypi-pico-sdk-xpack). The names below are examples:

Today in Moves to (example name)
-aarch32/soc/bcm2837, -aarch64/soc/bcm2837, soc/bcm2711, their drivers/ micro-os-plus-iii-devices-bcm283x
-aarch32/soc/rk3506, Lyra drivers micro-os-plus-iii-devices-rk3506
-cortexm/soc/rp2040, soc/rp2350 micro-os-plus-iii-devices-rp2xxx
-cortexm/soc/stm32f4xx micro-os-plus-iii-devices-stm32f4
-posix-arch/soc/native, host file block device stays in -posix-arch (it is the host “device”) or a small host package
drivers/fatfs/ in -aarch32, -aarch64, -posix-arch (a copy of ChaN FatFs: ff.c, ff.h, ffconf.h, plus a diskio glue) the FatFs sources come from upstream’s @xpacks/chan-fatfs dependency (P1); only the diskio glue stays with the device package

Each one exports its micro-os-plus::soc-<chip> targets, unchanged, so consumers do not change. Use git subtree split / filter-repo to keep the history, as the dissolution did in the other direction. The ports keep the architecture only.

The duplicate BCM2837 code in -aarch32 and -aarch64 (32- and 64-bit builds of the same chip) is a point to settle when moving: one package with both, or the shared parts only.

Check: the compile and link commands (compile_commands.json) of every configuration are identical before and after; the same tests pass.

9. Step 4: one place per board (R6)

Board facts move from <port>/test/boards/<b>/board.cmake into the platform folder, where upstream keeps them:

Board fact Goes to
CPU count, -mcpu, defines, LED pin, addresses tests/platforms/<P>/cmake/platform-library.cmake
Linker scripts tests/platforms/<P>/device/linker-scripts/ (as upstream NUCLEO and Pico)

The port library stops reading board.cmake, and BOARD disappears from the port. Each package’s tests/ (§10) has its own platforms/<P>/ for the boards it runs on, in the same shape.

Check, per board: identical compile_commands.json and ctest -N list before and after.

11. Step 6: portable running (R9)

QEMU and host tests: CTest runs the tool; run-qemu.sh and run-host.sh go.

Pick one test one add_test per program
Timeout per test set_tests_properties(… TIMEOUT <s>)

  COMMAND "${_qemu}" -M raspi3b -smp 4 -nographic -serial none
          -semihosting-config enable=on,target=native

Hardware tests: CTest runs openocd with a Tcl script; hw.sh and run-hw.sh go. OpenOCD contains a Tcl interpreter and runs on all three systems:

add_test (NAME "${PLATFORM_NAME}-${_app}-hwd"
  COMMAND openocd -f "${_platform_dir}/openocd/board.cfg"
                  -f "${_support_dir}/run-test.tcl"
                  -c "uos_run_test ${_bin}/${_app}-hwd.elf")
set_tests_properties ("${PLATFORM_NAME}-${_app}-hwd" PROPERTIES
  LABELS "hwd" TIMEOUT 600 RUN_SERIAL TRUE
  PASS_REGULAR_EXPRESSION "RESULT: PASS" FAIL_REGULAR_EXPRESSION "RESULT: FAIL")
run-hw.sh job OpenOCD Tcl
halt all cores foreach t [target names] { $t arp_halt }
load load_image <elf>
clear the secondary start slots mww at the __smp_spin address, passed from CMake
start core 0, resume parked cores resume <entry> per target
semihosting on some cores only arm semihosting enable per target
Pi 4 B watchdog / Lyra CRU reset in a separate session <board>-reset.tcl run by a CTest fixture
verdict semihosting SYS_EXIT ends OpenOCD; CTest reads RESULT:

The UART is never opened, as today. Boards with a reset line (NUCLEO, WeAct) can use upstream’s plain openocd … program … reset.

Actions in every package.json stay shell commands, as xpm intends, but portable ones: cmake -E, del-cli, Liquid {{ path.sep }}, no rm, ln, bash.

Confidence: QEMU part high (every piece already exists). Hardware part medium: each board’s sequence, especially resets that drop the debug link, must be checked on the board, one test at a time; each board keeps its hw.sh until its Tcl version passes.
